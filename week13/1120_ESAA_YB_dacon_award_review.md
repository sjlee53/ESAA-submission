각각 5.6 규제 선형 모델과 5.8 회귀 트리에서 배운 것이고, 셋을 평균 내는 방식도 5.10의 예측 혼합과 같다.
**책에서 배운 도구만으로 2,325명 중 2위를 한 코드**라서 읽는 의미가 있었다.

## 1. 데이터

임대주택 단지의 정보로 **그 단지에 등록된 차량 수**를 맞히는 문제다.

| 파일 | 내용 |
|---|---|
| `train.csv` | 단지 정보 + 정답 `등록차량수` |
| `test.csv` | 단지 정보만 |
| `age_gender_info.csv` | 지역별 나이·성별 인구 분포 |
| `sample_submission.csv` | `code`(단지코드) + `num`(등록차량수) |

변수는 이렇게 나뉜다.

- **단지 규모** — `총세대수`, `전용면적`, `전용면적별세대수`, `공가수`, `단지내주차면수`
- **단지 성격** — `임대건물구분`(아파트/상가), `공급유형`, `자격유형`, `지역`
- **비용** — `임대보증금`, `임대료`
- **접근성** — `도보 10분거리 내 지하철역 수`, `도보 10분거리 내 버스정류장 수`

**이 데이터의 핵심 구조는 "한 단지가 여러 행"이라는 점이다.** 같은 단지라도 전용면적 구간별로
행이 나뉘어 있다. 그런데 **제출은 단지 하나당 한 줄**이다. 그래서 행을 단지 단위로 합치는 작업이
전처리의 절반을 차지한다. 합치고 나면 학습 411개 단지, 평가 150개 단지가 된다.

결측치도 적지 않다. 학습 데이터에서 `임대보증금`·`임대료` 각 549건, `지하철` 207건이 비어 있고,
평가 데이터에는 `자격유형`도 2건 비어 있다.

## 2. 코드 흐름

```
컬럼명 정리 → 결측치 처리 → 범주 그룹화 → 숫자 매핑
   → 파생변수 생성 → 전용면적 구간화·상하한
   → 단지 단위로 행 합치기 (411 / 150)
   → GridSearchCV로 GBM 깊이 탐색
   → Lasso · ElasticNet · GBoost 학습 → 세 예측값 평균
```

| 단계 | 한 일 |
|---|---|
| 컬럼명 | 긴 이름을 `지하철`, `버스`로 줄임 |
| 결측치 | `자격유형`은 **뒤 행 값으로** 채움, `임대보증금`·`임대료`의 `'-'`는 결측 처리 후 **1로** 채움 |
| 범주 그룹화 | 공급유형 10종 → 6종, 자격유형 15종 → 4종으로 묶음 |
| 인코딩 | 범주를 정수로 매핑 (원-핫 아님) |
| 파생변수 | `전체면적합`, `건물가치`, `평균임대`, 55㎡ 기준 세대수, 아파트·상가 여부 |
| 면적 처리 | 5의 배수로 내림, 15~100으로 상하한 |
| 행 합치기 | 단지코드별로 면적·보증금·세대수를 **합산** |
| 모델 | Lasso(α=0.1), ElasticNet(α=0.1, l1_ratio=0.7), GradientBoosting(10,000그루) |
| 제출 | 세 예측값을 **1:1:1 평균** |

## 3. 주요 코드 분석

### (1) 여러 행을 한 단지로 — 이 문제의 본질

```python
total_area = train['전용면적'] * train['전용면적별세대수']
train['전체면적합'] = total_area

total_fee = train['임대보증금'] * train['전용면적별세대수']
train['건물가치'] = total_fee
average_fee = total_fee / train['총세대수']
train['평균임대'] = average_fee
```

그다음 단지코드별로 이 값들을 더해 한 줄로 만든다.

```python
for i, code in tqdm(enumerate(train['단지코드'].unique())):
    temp = train[train['단지코드'] == code]
    ...
    for j in range(number):
        lastvalue_area += train.iloc[change_index[i]+j]['전체면적합']
        lastvalue_fee  += train.iloc[change_index[i]+j]['건물가치']
        ...
```

면적과 세대수를 **곱한 뒤 더하는** 순서가 중요하다. `전용면적`은 구간별 값이고 `전용면적별세대수`는
그 구간에 몇 세대가 있는지다. 그냥 면적만 더하면 "84㎡ 구간이 있다"는 사실만 남지만,
세대수를 곱해 더하면 **단지 전체의 실제 연면적**이 나온다. 차량 등록 수와 직접 연결되는 양이다.

`평균임대`도 같은 구조다. 보증금 × 세대수를 더한 뒤 총세대수로 나눠 **한 세대당 평균 보증금**을 만든다.
이건 단지의 **경제 수준**을 나타내는 값이고, 소득이 높으면 차를 더 많이 가진다는 가정이 들어 있다.
글에서 "주상복합아파트의 적정 주차수요에 관한 연구(윤현석, 2007)" 논문을 참고했다고 밝혔는데,
파생변수가 통계적 탐색이 아니라 **도메인 문헌**에서 나왔다는 뜻이다.

### (2) 55㎡ 기준으로 세대를 가르기

```python
train['is_55미만'] = np.where(train['전용면적'] < 55, 1, 0)
train['is_55이상'] = np.where(train['전용면적'] >= 55, 1, 0)
train['temp_55미만'] = train['is_55미만'] * train['전용면적별세대수']
train['temp_55이상'] = train['is_55이상'] * train['전용면적별세대수']
```

전용면적을 **연속값이 아니라 두 덩어리**로 나눴다. 55㎡는 소형과 중형을 가르는 선이고,
작은 집은 1인·2인 가구가 많아 차가 적고 큰 집은 많다는 생각이 담겨 있다.

면적 자체도 손봤다.

```python
train['전용면적'] = train['전용면적'] // 5 * 5     # 5의 배수로 내림
train.loc[train['전용면적'] > 100, '전용면적'] = 100   # 상한
train.loc[train['전용면적'] < 15,  '전용면적'] = 15    # 하한
```

84.97㎡와 84.93㎡를 다른 값으로 두면 모델이 의미 없는 차이를 학습한다. 5의 배수로 묶어
**같은 평형끼리 한 값**이 되게 했다. 상하한은 아주 크거나 작은 면적의 영향을 자르는 처리다.

### (3) 모델 — 책에서 배운 것 그대로

```python
model_Lasso  = make_pipeline(RobustScaler(), Lasso(alpha=0.1, random_state=20))
model_ENet   = make_pipeline(RobustScaler(), ElasticNet(alpha=0.1, l1_ratio=0.7, random_state=20))
model_GBoost = GradientBoostingRegressor(n_estimators=10000, learning_rate=0.05, max_depth=4,
                                         max_features='sqrt', min_samples_leaf=10,
                                         min_samples_split=5, loss='huber', random_state=90)

predictions = (Lasso_predictions + ENet_predictions + GBoost_predictions) / 3
```

눈에 띄는 선택이 셋이다.

- **`RobustScaler`** — 선형 모델 앞에만 붙였다. 평균·표준편차 대신 **중앙값과 사분위 범위**로
  스케일을 맞추는 방식이라 극단값에 덜 흔들린다. `건물가치`처럼 단지 규모에 따라 값이 크게
  벌어지는 변수가 있어서 고른 것으로 보인다. GBM에는 안 붙였는데, 트리는 스케일에 영향을
  받지 않으니 맞는 판단이다.
- **`loss='huber'`** — GBM의 손실 함수를 후버로 바꿨다. 오차가 작을 때는 제곱,
  클 때는 절댓값처럼 동작해서 **이상치에 덜 끌려간다.** 평가 지표가 MAE이므로 제곱 오차보다
  지표에 가까운 손실이다. **지표에 손실 함수를 맞춘 것**이다.
- **1:1:1 평균** — 가중치를 따로 찾지 않고 그냥 셋을 똑같이 섞었다.

GBM의 `max_depth`는 GridSearchCV로 20겹 교차검증을 돌려 4로 정했다.

```python
parameters = {'max_depth': [1,2,3,4,5,6,7], 'random_state': [10,30,50,70,90]}
GS = GridSearchCV(model, param_grid=parameters, cv=20, scoring=rmse_scorer)
# 결과: {'max_depth': 4, 'random_state': 90}
```

## 4. 새롭게 알게 된 점 / 아쉬운 점

### 새롭게 알게 된 점

**평가 지표에 손실 함수를 맞출 수 있다.** 이 대회 지표는 MAE인데, GBM의 기본 손실은 제곱 오차다.
제곱 오차로 학습하면 큰 오차를 줄이는 데 힘을 쓰지만, MAE로 채점하면 그건 이득이 아니다.
그래서 `loss='huber'`로 바꿔 둘 사이를 맞췄다. 이번 주 필사에서 자전거 대회 지표가 RMSLE라
타깃을 로그 변환했던 것과 **같은 발상**이다. 그때는 데이터를 지표에 맞췄고, 여기서는 모델을
지표에 맞췄다. 지표를 먼저 읽고 거기서 거꾸로 설계한다는 점이 같다.

**스케일러를 모델마다 다르게 붙였다.** 선형 모델 두 개에는 `RobustScaler`를 파이프라인으로 묶고,
GBM에는 붙이지 않았다. 5.8에서 "트리는 값의 순서만 본다"를 배웠고 미니프로젝트에서 MinMax를
적용해도 점수가 0.0002밖에 안 움직인 걸 직접 확인했는데, 그 지식이 **코드 구조로 드러난** 사례다.
`make_pipeline`으로 묶으면 교차검증을 돌릴 때 폴드 안에서 스케일링이 이뤄져 누수도 막힌다.

**파생변수가 논문에서 나왔다.** 보통은 상관계수를 보거나 이것저것 만들어 보고 고르는데,
이 팀은 주차수요 연구 논문을 읽고 `평균임대`, `55㎡ 기준 세대수` 같은 변수를 설계했다.
미니프로젝트에서 저도 결합 이산화황을 만들었는데 그건 "total에서 free를 빼면 별개의 양"이라는
수준이었지, 양조학 문헌을 찾아본 건 아니었다. **데이터 밖에서 가져온 지식이 변수가 된다**는 걸
처음 제대로 봤다.

**연속값을 일부러 뭉갠다.** 전용면적을 5의 배수로 내리고 상하한을 씌운 처리가 인상적이었다.
84.97과 84.93의 차이는 의미가 없는데 모델은 그걸 구분하려 든다. 해상도를 낮추는 것이
정보를 버리는 게 아니라 **잡음을 버리는 것**일 수 있다.

### 아쉬운 점

**결측치를 1로 채운 근거가 없다.**

```python
train[['임대보증금', '임대료']] = train[['임대보증금', '임대료']].fillna(1)
```

549건, 전체의 적지 않은 비율이다. 0도 평균도 아닌 1을 고른 이유가 글에도 주석에도 없다.
게다가 이 값은 `건물가치`(보증금 × 세대수)와 `평균임대`의 재료로 쓰이고, `평균임대`는
`np.log(...)`를 거친다. 로그를 씌우니 0을 피하려고 1을 쓴 것 같은데, 그렇다면
**실제 보증금이 1원인 단지와 값이 없는 단지가 구분되지 않는다.** 결측 여부를 별도 변수로
남겼다면 모델이 "이 단지는 정보가 없다"는 사실 자체를 쓸 수 있었을 것이다.

**`자격유형`을 뒤 행 값으로 채웠다.**

```python
train['자격유형'] = train['자격유형'].fillna(method='backfill')
```

같은 단지의 다른 면적 구간이 바로 아래에 있다는 전제가 깔려 있다. 데이터가 단지코드 순으로
정렬돼 있으면 맞지만, **정렬이 보장되는지 확인한 흔적이 없다.** 바로 아래 행이 다른 단지면
엉뚱한 값이 들어간다. 결측이 평가 데이터 2건뿐이라 영향은 작았겠지만, 전제를 코드로 확인하지
않은 부분이다.

**범주를 정수로 매핑했다.**

```python
local_map = {}
for i, loc in enumerate(train['지역'].unique()):
    local_map[loc] = i
# '경상북도': 0, '경상남도': 1, '대전광역시': 2, ...
```

지역 16곳에 등장 순서대로 0~15를 붙였다. **순서에 아무 의미가 없는데 선형 모델은 크기로 읽는다.**
서울(14)이 경상북도(0)보다 14배 크다고 해석하는 셈이다. 이번 주 필사에서 자전거 데이터의
`year`를 2011·2012 그대로 뒀을 때 회귀 계수가 이상하게 커졌고, 원-핫으로 바꾸자 RMSLE가
1.017에서 0.59로 떨어졌던 것과 똑같은 상황이다. GBM은 구간을 잘라 쓰니 덜하지만,
**Lasso와 ElasticNet 두 모델에는 그대로 문제가 된다.** 원-핫으로 바꿨다면 점수가 더 올랐을
가능성이 있다고 생각한다.

**교차검증 점수가 없다.** GBM의 깊이를 고를 때만 GridSearchCV를 썼고, 최종 세 모델을 섞은 구성에
대해서는 검증 점수를 전혀 출력하지 않았다. 1:1:1이 최선인지, 두 개만 섞는 게 나은지 비교한
흔적이 없다. 미니프로젝트에서 TabICL 비중을 0.25·0.5·1.0으로 바꿔 가며 그룹 교차검증으로
확인했던 것과 대비된다. 리더보드 점수만 보고 골랐다면 **697행 표본에 맞춘 선택**이었을 수 있다.

**`n_estimators=10000`에 조기 종료가 없다.** 1만 그루를 전부 학습한다. 학습률이 0.05이고
`min_samples_leaf=10` 같은 제약이 있어 과적합이 심하진 않겠지만, 검증 세트로 조기 종료를 걸었다면
몇 그루에서 멈춰야 하는지 알 수 있었을 것이다.

### 우리 프로젝트에 적용한다면

와인 데이터에는 "여러 행이 한 단위"인 구조가 없어서 행 합치기는 쓸 일이 없다. 다만 **지표에
손실 함수를 맞추는 발상**은 가져올 만하다. 우리 지표는 정확도였고 오답의 89.6%가 인접 등급이었는데,
그렇다면 인접 등급 오답에 덜 벌점을 주는 순서형 손실을 쓰는 쪽이 지표와 더 가까웠을 수 있다.
